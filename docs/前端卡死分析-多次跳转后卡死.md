# 多次跳转后卡死 — 纯前端层面分析

## 前置：跳转链路上的所有请求

每次搜索页 → 详情页 → 回退搜索页 → 再次进入详情页的完整循环中，浏览器**同时**发出的 fetch 请求：

### 搜索页（search.js）单个页面周期内的请求

| 请求 | 触发时机 | 行号 | 有 AbortController? |
|------|---------|------|--------------------|
| GET `/api/search?q=...` | fetchResults() | search.js:86-100 | ❌ 无（只有局部超时定时器，没有关联的 AbortController） |
| POST `/api/wishlist/check` | renderResults() 时批量查收藏状态 | search.js:146-161 | ❌ 无 |
| GET `/api/search-history` | 页面加载 | search.js:416-441 | ❌ 无 |
| POST `/api/jobs` | quickDownload | search.js:280-309 | ❌ 无 |
| POST/DELETE `/api/wishlist/…` | toggleWishlist | search.js:314-366 | ❌ 无 |

### 详情页（detail.js）单个页面周期内的请求

| 请求 | 触发时机 | 行号 | 有 AbortController? |
|------|---------|------|--------------------|
| GET `/api/album/<id>` | IIFE 立即执行 | detail.js:18 | ✅ 有（15s 超时） |
| GET `/api/library/<id>/tags` | renderAlbum → loadAlbumTags | detail.js:298-309 | ❌ 无 |
| POST `/api/library/<id>/tags/sync` | renderAlbum 成功后 fire-and-forget | detail.js:29-39 | ❌ 无 |
| GET `/api/wishlist/<id>` | IIFE 立即执行（收藏状态检查） | detail.js:216-229 | ❌ 无 |
| POST `/api/jobs` | createDownloadJob | detail.js:198-212 | ❌ 无 |
| POST/DELETE `/api/wishlist/<id>` | 收藏按钮 click | detail.js:240-285 | ❌ 无 |

### 每个详情页最多同时发出 4 条请求
加上搜索页残留的请求，多次跳转后累计 pending 请求很容易**填满 HTTP/1.1 每个域名 6 个并发连接的限制**。

---

## 根因 1：没有任何页面切换时的 fetch 清理 ← 最核心问题

### 缺少 `pagehide` / `beforeunload` 中的 fetch abort

**`search.js`** 没有 `beforeunload` 或 `pagehide` 处理函数来 abort 正在进行的 fetch。
**`detail.js`** 也没有。

当用户点击卡片（`<a href="/album/123">`）从搜索页导航到详情页时：

1. 搜索页的 `POST /api/wishlist/check` 仍在 in-flight
2. 浏览器对 `<a>` 导航执行**整页替换**（非 SPA），fetch 请求被浏览器取消
3. **但 TCP 连接不会立即释放** — 如果服务器端响应慢（例如 `search_albums()` 调用 JMComic 外部 API 耗时 >10s），连接可能处于 CLOSE_WAIT 状态
4. 用户进入详情页 → 详情页再发 3-4 条新 fetch
5. 用户快速点击"返回搜索" → search.js 不清理旧状态 → `pageshow` 再发新的搜索请求

**累积效应：几轮跳转后，浏览器连接池被慢请求填满，后续请求全部排队，页面失去响应。**

### detail.js 的 `pageshow` / `pagehide` 完全缺失

`search.js` 有 `pageshow` 事件处理（L495-515），但 `detail.js` 没有。这意味着：

- 如果用户从详情页用"返回搜索"回到搜索页，再立即点另一个卡片进入详情页
- 浏览器可能从 bfcache（页面缓存）恢复详情页 + 执行 IIFE
- IIFE 中的 AbortController 是全新的，但之前未完成的连接没有清理路径

## 根因 2：`detail.js` 全局 `document` 事件监听器不断累积 ← 内存泄漏

`detail.js` 第 232 行：

```js
document.addEventListener('click', function (e) {
    var btn = e.target.closest('#wishlist-toggle-btn');
    // ...
});
```

这是一个**全局事件监听器**，直接绑在 `document` 上。IIFE 每次执行都添加一个新的监听器：

- 第 1 次进详情页 → 1 个 listener
- 第 5 次进详情页 → 5 个 listener
- 第 20 次进详情页 → 20 个 listener

**后果：**
- 每次点击收藏按钮，**所有累积的监听器同时触发** → 20 条 fetch 并发发出
- 内存中闭包（每个 listener 都持有 `albumId` 等变量的引用）不断累积
- 这是典型的逐步变慢直至卡死的模式

### 同样的问题在 `detail.js` 的 `bindEvents` 中

`bindEvents(album)` 在第 155-195 行：
- 用 `addEventListener` 绑在 DOM 元素上（`download-selected-btn`、`download-all-btn` 等）
- 这些元素每次 `renderAlbum()` 被**重建**（`container.innerHTML = html`），所以旧的监听器随旧 DOM 自动销毁
- 因此这部分**不泄漏** — 但 `document` 上的监听器不受 innerHTML 替换影响

## 根因 3：`search.js` `renderResults()` 中的 wishlist/check 是竞态隐患

```js
// search.js L145-161
fetch('/api/wishlist/check', { ... })
.then(function (r) { return r.json(); })
.then(function (checkData) { ... })
.catch(function () { console.warn(...); });
```

问题：
- **没有 AbortController** — 用户快速翻页时，上一页的 `POST /api/wishlist/check` 还在飞
- **没有检查页面是否已卸载** — `.then()` 回调中直接操作 DOM，在页面已卸载后可能触发看不见的错误
- **没有去重** — 如果用户快速连续翻页，多个 `renderResults()` 调用会发出多个并发的 wishlist/check 请求
- **这个请求是搜索结果的附属请求** — 如果服务器端响应慢（不设超时），直接占用一个连接槽

## 根因 4：`detail.js` fire-and-forget 的 tags/sync 请求

```js
// detail.js L29-39
fetch('/api/library/' + encodeURIComponent(albumId) + '/tags/sync', { method: 'POST' })
    .then(function (r) { return r.json(); })
    .then(function (syncData) { ... })
    .catch(function () { /* 静默失败 */ });
```

这是发后即忘的请求：
- 没有 AbortController
- 没有超时
- 如果 18comic 服务器响应慢，这个请求可能挂起几十秒
- 用户此时已跳转到其他页面，但连接仍然占用

## 根因 5：bfcache 与搜索页的交互问题

`search.js` L495-515 的 `pageshow` 处理：

```js
window.addEventListener('pageshow', function (event) {
    if (event.persisted) {
        // 重新获取元素引用 + 触发自动搜索
        searchForm = document.getElementById('search-form');
        // ...
        fetchResults();  // ← 重新触发搜索请求
    }
});
```

当用户从详情页点"返回搜索"（或浏览器后退按钮）：
1. 搜索页从 bfcache（前进/后退缓存）恢复
2. `pageshow` 事件触发 → 执行 `fetchResults()` → 发新的 `GET /api/search?q=...`
3. 但此时**bfcache 恢复的页面中，之前的 JS 执行上下文是冻结后恢复的**
4. `search.js` 的 IIFE 作用域中，`currentQuery`、`currentPage` 等变量保持离开时的值
5. 如果之前的 `fetchResults()` 的 `.then()` 回调在 bfcache 恢复后继续执行（即 Promise 在页面隐藏期间完成了），可能会和新的 `fetchResults()` 形成**双重渲染竞态**

**实际风险较低但存在：** Promise microtask 在 bfcache 中可能排队，恢复后新旧两个搜索结果渲染到同一个 DOM 容器中。

## 根因 6：静态资源一年强缓存（次要但后果严重）

`app.py` L199：
```python
app.config["SEND_FILE_MAX_AGE_DEFAULT"] = 31536000  # 1年
```

所有静态 JS/CSS 文件被浏览器缓存 1 年。如果发布过一次带 bug 的版本（如搜索卡片未用 `<a>` 包装、缺少 `fetchWithTimeout`），用户浏览器在一年内不会拉取修复版本。

这不会直接导致卡死，但会导致**修复无法生效**。

## 与服务器端问题的交叉验证建议

### 客户端优先排查
1. **重现卡死后查看 `chrome://net-internals/#sockets`** — 看看 6 个连接是否被填满，哪些请求处于 pending 状态
2. **重现卡死后看 console** — `detail.js` 的 `document` 事件监听器数量：`getEventListeners(document)` 或 `$._data(document, 'events')`
3. **检查 `/api/album/<id>` 响应时间** — 如果 server 调用 18comic 外部 API 过慢 (>15s)，多次跳转累积的 pending 连接数会剧增

### 服务器端排查建议
4. 检查 `waitress` 的线程池（配置为 128 线程）是否被慢请求（调用 18comic 外部 API）耗尽：
   - `grep "HTTP GET /api/album/"` 看接口耗时分布
   - 如果 `/api/album/` 平均耗时 >5s，说明服务端线程被外部 HTTP 调用阻塞，客户端连接无法快速释放
5. 检查 `/api/wishlist/check` 是否有数据库慢查询

### 交叉证据 — 连接池 + 线程池双重耗尽
最可能的情况是**前端连接池和后端线程池同时瓶颈**：
- 用户快速跳转 → 多个 `/api/album/<id>` 同时发出 → waitress 128 线程池被外部 HTTP 调用阻塞 → 响应慢（>10-15s）
- 浏览器 6 连接池被这些慢请求填满 → 新请求排队
- 前端路由是整页替换（非 SPA）→ bfcache 恢复 + pageshow 再发请求 → 加重拥堵
- `detail.js` 的 `document` 监听器累积 → 后续进入详情页时 fetch 数量翻倍 → 瀑布效应

## 修复建议优先级

### P0 — 立即修复（直接影响卡死）

1. **`detail.js`: 移除全局 `document` click 监听器，改用事件委托只绑定一次**
   ```js
   // 改为：用一个挂载在 window 或 document 上的单例处理函数
   // 详细：移除 line 232 的 addEventListener，改用 base.html 或自执行代码中
   // 一次性绑定的委托监听
   ```

2. **`search.js` + `detail.js`: 所有 fetch 加上 AbortController，并在 `pagehide` 中 abort**
   ```js
   window.addEventListener('pagehide', function () {
       if (controller) controller.abort();
   });
   ```

3. **`detail.js`: 给所有 fetch（不仅是 album detail）加上超时**
   - 特别是 loadAlbumTags、wishlist check、tags/sync 这些附属请求

### P1 — 重要的

4. **`search.js`: `renderResults()` 中的 wishlist/check 加上 AbortController，** 并在新的 `fetchResults()` 开始时 abort 旧的
5. **`detail.js`: 在 IIFE 顶部 abort 上一次 IIFE 留下的未完成请求**（通过闭包共享的 AbortController 引用）

### P2 — 验证性

6. 配合服务器端确认 `/api/album/<id>` 的 P95 响应时间，看是否需要给客户端 15s 超时加长（当前 15s 可能太短）
7. 验证 `beforeunload` 在您的 Electron / Chromium 环境中是否可靠触发

## 结论：最可能原因排序

| 优先级 | 原因 | 置信度 |
|--------|------|--------|
| **1** | **`detail.js` `document` click 监听器多次注册不清理 → 累积 → 多次跳转后每次点击触发数十条 fetch → 连接池爆满** | ★★★★★ |
| **2** | **所有 fetch 不设 AbortController，页面切换不清理 → 残留 pending 请求逐渐填满 6 连接池 → 新请求排队 → 页面卡死** | ★★★★★ |
| 3 | bfcache 恢复时 `pageshow` 重新触发搜索 + 旧 Promise 未完成 → 双重渲染 + 连接争用 | ★★★☆☆ |
| 4 | 服务器端外部 API 调用慢（/api/album/ 调用 18comic）→ 响应时间长 → 连接释放延迟 | ★★★☆☆ |
| 5 | 静态资源一年缓存导致修复不生效 | ★★☆☆☆ |
