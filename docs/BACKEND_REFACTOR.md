# Windows 优先的后端重构

开发分支：`codex/refactor-windows`。核心继续使用 Python 与官方 jmcomic，前端主题、页面和依赖版本在这一阶段保持原状。

## 第一批已建立的边界

### 资源目录独立于任务历史

数据库 schema v3 增加 `resource_catalog`，保存成功下载的路径、章节选择、排序依据及 superseded 信息。升级时在事务中回填旧的完成任务，之后通过数据库触发器与完成状态写入保持原子性。

- 删除/清理任务历史保留资源记录及文件，资源库、阅读、标签、收藏、批量条件和更新检查继续可用。
- 将已完成状态更正为非完成状态会撤销该次完成证据；它与删除历史是不同操作。
- 最新成功资源仍是权威依据。旧目录被重新创建后，新任务失败或取消留下的残页不能冒充过去完成的资源。
- `database.get_completed_job_by_album_id()` 暂时保留兼容名称，但返回的是成功资源快照，不保证原任务历史仍存在。新代码优先使用 `resource_records()`。
- 数据库升级是增量迁移，不删除/移动下载文件。不应在未备份的日常实例上进行迁移试验。

### 任务命令

`core/task_commands.py` 管理入队和重试的事务，不负责启动线程或联网。

- 同专辑、相同章节集合的 queued/running/paused 任务复用；章节顺序不影响匹配。
- 整部下载（空章节选择）与显式部分章节不同；不同章节仍可排队，由调度器保证同专辑串行。
- 重试来源检查、目录继承、任务插入与收藏状态同步在同一事务完成。
- 复用任务不覆盖已有目录，不把 running/paused 的收藏状态降为 queued。
- `/api/jobs` 与重试接口保留 `status/job_id`，新增 `created/reason`：新建201、复用200；损坏的重试来源返回409。
- 当前仅保证活跃任务范围的幂等，不声明跨完成生命周期的永久幂等键协议。

### 文件发布

`core/storage.py` 提供 `staged_file()` 和 `is_temporary_path()`：

```python
with staged_file(target) as staged:
    write_image(staged.path)  # 保留 SDK/Pillow 所需的真实扩展名
    staged.publish(validate_image)
```

- 暂存位于目标同盘的 `.jmcomic-staging/attempt-*/`，校验成功后原子发布。
- 失败保留旧文件，退出只清理本次文件与空目录，不递归删除未知内容。
- 校验目录身份、符号链接/junction 与文件类型，拒绝被替换的暂存路径。
- 阅读、封面、可读状态、打包、导出及归档成员索引共用排除规则；猜测临时页 URL 也不能读取。
- 旧版数字页码加8位随机名的 `.webp/.gif` 临时页只被过滤，不自动删除。普通带点图片名和合法目录仍可使用。
- 打包器在完整写入并验证条目数与 CRC 后发布，保留原有增量页合并规则。

### 上游错误边界

`core/upstream.py` 把 SDK/transport 异常映射为稳定种类，公开响应不携带上游正文、代理凭据或原始异常文本。原始原因通过异常链和 request_id 日志保留。

| 种类 | HTTP | 含义 |
|---|---:|---|
| timeout | 504 | 真实等待或传输超时 |
| connection / tls | 502 | 连接或安全连接失败 |
| access_denied | 502 | 上游401/403，区别于本程序的访问权限 |
| http_error | 502 | 上游HTTP错误，另附 upstream_status |
| invalid_response | 502 | 非JSON/响应结构无法解析 |
| not_found | 404 | SDK明确确认漫画或章节不存在 |
| upstream_error | 502 | 其他边界内的上游失败 |

保留原有 `status/message`，增加 `error_kind` 和必要的 `upstream_status`。多节点混合失败不会因为其中一个超时就全部报504；本地数据库或程序错误仍为500。超时返回后，仍在运行的 SDK 调用继续持有客户端租约，避免提前关闭连接。

诊断页容忍新 SDK 移除旧 `DOMAIN_HTML` 属性，仍只读取已知域名，不为诊断触发域名发现。此项不代表已经完成新版 SDK 的全部兼容验证。

## 第二批：运行生命周期与共享 SDK 构造

### 应用生命周期

`core/runtime.py` 的 `ApplicationRuntime` 统一后台服务所有权，先恢复中断任务，再依次启动任务调度、定时调度和更新检查；部分启动失败按逆序清理，包括已经获取资源但启动抛错的组件。

- `create_app()` 仍只初始化数据库与 HTTP 应用，不恢复或启动任务。
- `main()` 先获得单实例锁和监听端口，再恢复任务、启动后台服务；端口绑定失败不会重排任务或开始下载。
- 常规退出、服务异常和信号退出共用清理路径，停止预算由 Runtime 统一分配，不再各组件独立累加等待。
- 定时调度和更新检查的 `stop(timeout=...)` 返回排空结果，未退出的线程仍保留引用；不会在它退出前重建另一条线程。
- 未排空时主入口返回失败，保留日志及 Windows 单实例锁，直到旧进程实际退出由系统释放，避免替代进程与旧执行器并发写入。

### 暂停、取消与停机分开处理

`core/task_commands.py` 提供事务化的中断恢复和恢复暂停命令，`JobManager` 负责执行器生命周期。

- 重启仅将没有执行器的 `running` 恢复为 `queued`；用户主动 `paused` 保持暂停，终态不改。
- 点击恢复时，有执行器的暂停任务恢复 `running` 并唤醒；重启后没有执行器的任务先回到 `queued`，按现有并发/时间段规则调度。
- `request_stop()` 立即关闭领取入口并唤醒暂停等待；`stop(timeout=...)` 在一个总预算内等待调度器和工作线程。
- 停机中的执行器协作返回后，仅把仍为 `running` 的任务重排。暂停、取消、已完成和失败保持原状态，不把关闭伪装为成功完成或用户取消。
- 下载会在请求之间、图片发布前、重试前和完成写入前检查停机意图；因停机结束的请求不登记为失败页，不开始新重试。
- 在途 SDK 请求无法被 Python 线程安全强制中断。若它尚未结束，停止返回未排空并保留客户端和执行器所有权；没有承诺整个进程一定在预算内退出。
- 暂停/恢复的数据库状态与唤醒操作串行，防止旧暂停通知覆盖刚发出的恢复通知。

### SDK 与 CLI

`core/sdk_adapter.py` 集中 SDK 配置与 option/client 构造；导入适配器本身不初始化日志、数据库或网络。

- API/HTML 域名仍分别由 SDK 选择，自动更新域名与初始化 Cookie 请求的开关维持关闭。
- Web 保留已有的客户端租约与缓存，只通过适配器创建实例；图片/检查客户端仍可传操作专用参数。
- CLI 先初始化项目数据库，使用同样的代理、超时、客户端类型和下载目录配置；批量下载显式传递 option。
- CLI 使用 option 缓存客户端，使关闭操作作用于 SDK 顶层下载实际使用的传输，而非另建一个闲置客户端。
- 本批没有升级 SDK 或依赖，也没有改变 CLI 下载与 Web 任务队列之间的产品关系；CLI 下载仍是显式命令执行。

## 第三批：数据目录与备份恢复

前两批已验证改动保存为本地里程碑 `94b94b4`，未推送远端。第三批继续在同一重构分支开发。

- `core/path_utils.py` 分开代码资源与实例数据，提供启动时固定的目录配置；默认沿用原目录，环境变量支持独立数据、下载、缓存和备份位置，不自动移动个人数据。
- launcher 的虚拟环境和指纹仍来自代码位置，日志/启动记录和子进程环境跟随实例目录。设置中的只读下载路径取实际配置。
- `core/backup.py` 使用 SQLite backup API 与有界完整性校验，区分数据库快照、数据库/资源清单、完整资源三类用途。哈希、CRC、清单和数据库校验通过后原子发布。
- `core/restore.py` 校验后恢复到全新实例目录，按源下载根逐组件重映射路径；不覆盖已有目录，不自动启动任务，保留收藏、标签和检查基线，暂停保持暂停。
- 旧数据库在任何迁移写入前自动生成数据库快照；失败则停止初始化，未来版本数据库拒绝打开。迁移快照不扫描资源，但记录源根以便恢复。
- `core/instance_lock.py` 共用于服务、维护和 CLI 直接下载，沿用旧 Windows mutex 名称，防止备份期间仍有自家下载写入。未排空停机仍保留原有保护。
- CLI 新增 `backup`、`backup-info`、`restore --to`。备份中包含私密数据库内容，默认输出目录已忽略；本批不增加 HTTP 维护接口或 UI。

使用方式、备份包含范围、恢复路径及环境切换见 [数据维护文档](DATA_MAINTENANCE.md)。真实个人实例没有执行这些操作。

## 第四批：下载停滞与设置保存

### 下载请求和队列恢复

- `core/transfer.py` 给独占客户端的实际 GET/POST 设置剩余总预算，并通过公开的 libcurl session 配置约束连接与低速停滞；预算跨 SDK 重试共享，退出时恢复原传输方法、选项和重试策略。
- `core/image_download.py` 沿用 SDK 的图片请求、解密与转换，仅在 SDK 维护的图片域名之间切换；保留路径与查询参数，不新增永久域名。图片尝试次数受已保存的重试设置限制，多次尝试共用一个预算。
- 队列下载的专辑/章节元数据与每张图片均使用已保存的网络超时（上限120秒）。图片首轮与补偿轮各有一次预算，补偿轮不再隐含等待10分钟。不是整个大任务只允许运行一个超时时长。
- 请求必须实际返回、章节与图片执行器实际退出后才释放队列容量。没有分离仍在下载的线程，也不会并发关闭在途 libcurl 句柄。停机/取消在请求边界检查，在途请求仍可能等待剩余预算；此保证不覆盖任意 Python 代码死锁或图片转换挂起。
- schema v4 增加独立 `queued_at`：正常重启或执行器退出后，中断任务追加到已有等待队列之后，保留原创建时间及中断任务之间的先后顺序。暂停仍保持暂停，没有执行器的暂停任务点击恢复时追加队尾。
- v4 备份恢复同样把中断任务追加队尾；较旧备份保持原恢复行为，升级后使用新排队字段。

### 设置保存与草稿

- 设置页初次读取按字段合并：保留用户已编辑的值，填入其余已存设置；读取未成功之前不允许整表提交，避免把占位默认值误存。
- 保存与导入互斥，重复提交不产生并发保存。保存响应不会覆盖请求期间的新编辑；失败保留草稿，只有服务器明确成功才显示保存成功。读取配置禁用缓存。
- 数据库提交与立即应用区分处理：客户端缓存或调度器应用失败时，响应明确表示已保存并附提示，不再把已提交的数据误报为保存失败。
- 修复自动打包与删除原目录开关的异步联动，以及已有合法 socks 代理阻止其他设置保存的问题。沿用 eye-care 主题，没有调整页面布局与视觉样式。
- 临时实例中的独立进程已验证保存后退出、重新读取仍保留配置；未复现 SQLite 自行丢失已提交配置，不能据此断言用户历史问题只有一个原因。

## 第六批：Windows协作停机与完整服务自检

- `core/process_control.py` 使用随机令牌对应的Windows命名事件通知主线程；停机工作仍由主线程的统一finally路径负责，不新增HTTP停机接口。事件观察线程排空后才关闭句柄，错误不会伪装成成功。
- 启动器按回车/Ctrl+C退出、替换旧代码服务时先通知、再等待真实进程退出。重新核实PID与实例记录，身份变化、通道缺失、超时均保留进程并取消替换。旧服务没有新协议时提示从原启动窗口关闭，启动失败清理也不再推测无事件等于可以强杀。
- `core/http_server.py` 管理实际Waitress listener/channel/worker；停机结束SSE订阅、使用HTTPChannel的关闭路径唤醒输出背压等待，工作线程没有实际退出就不报排空成功。
- 正常结束服务入口时清理PID与端口记录，但实例mutex一直保留到操作系统确认进程退出。在线阅读预取与共享元数据future尚未全部纳入Runtime，这条保守边界避免它们存活期间另一服务或维护操作获得实例所有权；本批没有宣称能取消或排空这些后台请求。
- 启动器在操作已有服务之前只读核实数据库schema；未来版本数据立即拒绝，不停止较新服务、不写数据库。原迁移快照与恢复到新目录的回退方式继续有效，不增加原地降级。
- 新增 `lifecycle-check`，在带一次性nonce的临时根内以独立mutex两次运行真实 `app.main()`；通过HTTP保存设置，经Windows事件退出，重启后核实设置、暂停保留与中断任务恢复。普通入口仍使用原生产锁，worker连接只允许本机；源码重定向PID通过启动令牌与健康记录绑定。
- 构建发布需同时通过打包资源/API自检和完整服务生命周期自检，两份结果随ZIP保存。候选包仍沿用eye-care浏览器UI，没有更改运行依赖或上游SDK源码。
